# 项目知识图谱方法论

## 1. 定位与分工

- 全局 skill（本文件）只定义方法论：节点是什么、关系词汇、文件格式、维护和检索纪律。
- 图数据本身按项目存放，在该项目的 memory 目录下（`~/.claude/projects/<project>/memory/GRAPH.md`），随项目积累，不是全局共享的一份图。
- 诚实边界：这不是知识图谱数据库或查询引擎，没有编程遍历/查询能力。"检索效率"来自"grep 一份体积小、结构化的索引文件"，取代"翻遍每条 memory 正文猜有没有关联"，不是数据库式的查询性能。遍历关系仍然是打开链接指向的 memory 文件、人工读、人工推理。

## 2. 节点 = 现有 memory 文件

- 复用 memory 文件 frontmatter 里的 `name` 字段作为节点 ID，不新建一套平行的实体系统。
- 不给还没有对应 memory 记录的抽象概念单独建节点；先有事实（memory 文件）才谈关系，图不能脱离 memory 系统单独存在。

## 3. 关系词汇（固定、小集合，不随意扩展）

- `depends-on` — A 依赖/假设 B 成立，理解或应用 A 之前最好先看 B。
- `caused-by` — A 是 B 导致的（症状 -> 根因方向）。
- `supersedes` — A 取代了 B（B 过时但仍保留供追溯，当前以 A 为准）。
- `relates-to` — 弱关联，前三个都不贴切时的兜底，不能滥用成"看起来都提到同一个模块就加边"的万能标签。
- 需要表达这四个都覆盖不了的关系时，先判断是不是真的需要新词汇，需要的话问用户要不要扩展这个词汇表，不要自己随手加新词——词汇表越小，检索和判断成本越低。

## 4. GRAPH.md 格式

- 位置固定：`<project-memory-dir>/GRAPH.md`，跟 `MEMORY.md` 同级。
- 只放结构化关系，不放叙事文字——叙事留在各 memory 文件正文和 `MEMORY.md` 的一行摘要里，避免出现两份内容有重叠又容易失步的索引，这是刻意的克制，不是遗漏。
- 每行一条边，固定格式：
  ```
  - [[A]] --关系--> [[B]]
  ```
  例如：`- [[zig-cc-implicit-ndebug-on-optimization]] --relates-to--> [[logs-directory-for-build-acceptance-output]]`
- 按 A 节点分组即可，不需要额外的图可视化或第二种存储格式；文件顶部保留一行指回本 skill 的说明，不重复解释方法论。

## 5. 维护纪律

- 新建一条 memory、或在处理任务过程中发现两条已有 memory 之间存在真实关系时，在同一个动作里把边写进 GRAPH.md——跟"写 memory 正文时同步更新 MEMORY.md 索引"是同一条纪律，不能只做一半。
- 关系要基于真实、能一句话说清楚"为什么连"的判断；宁可不加边，也不加一条说不清楚原因、纯粹因为"看起来都跟同一个东西有关"就连上的边——图的价值来自关系可信，不是覆盖率。
- 不强制回填历史 memory 之间的关系；新建/后续因为任务需要重新触碰到某条旧 memory 时顺手补上关系即可，不为了这件事单独开一轮任务去梳理全部历史记录。

## 6. 检索纪律

- 进入一个不熟悉、但项目里已经有相关 memory 积累的任务前，除了看 `MEMORY.md` 的一行索引，还要 `grep` 一下 `GRAPH.md` 里有没有相关节点名——这一步专门用来捕捉"关键词不重合、但结构上有关系"的记忆，弥补纯关键词/语义匹配的召回盲区。
- 顺着边找到的其它节点，同样要读一遍对应 memory 文件正文再引用，不能只凭 `GRAPH.md` 一行关系描述就下结论或对外表述成事实。

## 7. 触发时机（不是所有项目都要建）

- 项目 memory 记录很少（个位数）、彼此明显没有强关联时，默认不主动新建 `GRAPH.md`；先按已有 memory 系统（`MEMORY.md` + 正文里的 `[[name]]` 提及）正常运作即可，避免为了还不存在的规模问题预先建一套用不上的结构。
- 触发点：某个项目的 memory 记录明显变多、或者真的发生过一次"应该关联但没关联上、返工过"的漏判，或用户明确要求，再建立/开始正式维护这个项目的 `GRAPH.md`。
