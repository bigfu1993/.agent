# 案例分析与汇报文档

## 核心原则

把文档当作一条可复核的论证链，而不是一次文案缩写。质量标准是“描述准确、证据充足、语意顺畅、不重复”，不是文件行数越少越好。

始终遵守四条底线：

1. 源证据决定结论，不为了叙事完整而补造数据。
2. 汇报稿必须能够脱离源文档独立阅读，但不需复制源文档的全部过程日志。
3. 正确性、性能、体积、可维护性等指标分开表达，不把一类证据换算成另一类收益。
4. 完整公开已证实收益、无明显收益、轻微趋势、暂缓项和证据缺口。

## 先确定文档职责

| 产物 | 主要职责 | 必须保留 | 不应承担 |
|---|---|---|---|
| 案例分析/技术复盘 | 作为长期证据库和决策记录 | 背景、时间线、原因、方案、数据、边界和未完成项 | 演讲节奏和页面时长限制 |
| 汇报稿/演讲文档 | 在限定时间内建立完整、可讲述的论证链 | 听众需要的背景、定位方法、量化结果、限制和推广结论 | 完整 commit 清单和每次试错细节 |
| 幻灯片/PPT | 为口头演讲提供视觉节奏 | 一页一个核心观点、图表和口头补充线索 | 完整正文和密集长表格 |

当用户要求“案例分析”和“汇报稿”时，默认将它们作为两份职责不同的产物；汇报稿以案例分析为数据源，不覆盖或反向削减源案例。

## 工作流程

### 定义输出契约

在动笔前确定：

- 听众、用途、建议时长和交付格式。
- 文档是源案例、汇报稿、管理层摘要，还是幻灯片内容源。
- 必须覆盖的分类维度、时间范围、当前状态和明确非目标。
- 哪些结论已验证，哪些只是假设、临时归因或后续计划。

用户已明确给出结构时直接执行，不另造一套目录。数据口径不明或对外发布风险较高时，先澄清再定稿。

### 建立证据台账

先读源材料，再编排叙事。定向检索当前实现、历史提交、运行日志、A/B 数据、旧文档和回撤记录，并区分“当前有效”、“历史暴露”、“已回撤”和“待验证”。

对每个重要结论至少记录：

| 字段 | 说明 |
|---|---|
| 结论 | 想要证明的具体变化 |
| 维度 | 正确性、耗时、频率、体积、分配、视觉或维护性 |
| 基线 | 改造前同口径数据；没有时明确写无基线 |
| 结果 | 改造后数据、样本数和环境 |
| 计算 | 原始值、公式、舍入方式和单位 |
| 证据 | 代码、commit、日志、自动测试、真实环境或人工视觉验收 |
| 边界 | 该数据能证明什么，不能证明什么 |

证据冲突时停止润色，回到源头核对环境、版本、时间窗口和统计口径；不挑选最有利的数据自行消解冲突。

### 组织叙事主干

除非用户指定其他结构，默认使用以下主干：

1. **问题发生的背景和问题描述**：业务、系统链路、运行尺度、用户影响和问题形成机制。
2. **定位方案**：追查顺序、埋点、对照实验、正确性不变量和关键判定依据。
3. **量化的可评估指标**：指标名称、计算口径、验收标准和证据等级。
4. **优化后的结果和提升对比**：基线、结果、降幅/增幅、无回归证据和解释边界。
5. **推广总结**：可复用方法、适用场景、必须保留的约束和触发重新评估的条件。

汇报稿可在正文前增加结论摘要，在文末视听众需要补充演讲节奏提示；不用摘要代替正文论证，也不单独设置附录或数据说明章节——量化口径已经在证据台账和正文表格里交代清楚，重复摘出反而制造冗余。

### 写成独立可读的正文

- 先介绍系统、术语和口径，再引用数字或缩写；不假设读者已打开源案例。
- 标题只写语义名称，不添加 `1.`、`1.1`、`一、` 等章节序号；需要表达顺序、步骤或可引用条目时，在正文中使用有序列表。
- 因果链、方案取舍和数据解释用连续段落；并列问题、步骤、约束和检查项用列表；同口径对比用表格。
- 不把整份文档写成列表，也不为了“丰富”而把每一句都做成小节标题。
- 合并前检查两段是否回答同一问题、使用同一证据，以及删掉一段是否不会丢失独立事实。只有三项都成立时才合并。
- 不用行数、字数或页数降幅判断“美化”是否成功。精简后如果丢失问题机制、判定依据、指标定义、精确结果或推广边界，立即恢复。
- 保留对结论有独立信息价值的细节，把逐 commit 叙事、重复日志和已被替代的中间方案放回源案例文档本身，不新增独立附录章节承接。

### 严格管理量化口径

- 降幅默认按 `(baseline - result) / baseline × 100%` 计算；增幅、倍数和百分点需明确区分。
- 表格中同时保留基线、结果、单位、样本量和结论边界。分项显示值与未舍入总计存在尾差时主动说明。
- 没有同口径基线时，只报告当前测量和预算占比，不宣称“提升”。
- 正确性数据（如全部成功、无协议错误）只证明无回归，不换算为性能百分比。
- 文件体积、源码行数和资源数量不直接等同运行耗时、FPS 或内存收益。
- 完整样本、稳定尾段、峰值和分位数结论不同时并列呈现，不只保留最有利的窗口。
- GC/内存优化优先量化“已审计路径中每帧显式分配次数”。没有 GC pause、heap 峰值和长稳态内存 A/B 时，不换算成停顿毫秒或内存降幅。
- 暂时归因于外部系统或上游限制的问题，写明触发重新归因的条件。

### 让图表承担论证，而不是装饰

- 一张图只承担一个主结论：链路图说明数据/状态流向，分组柱图说明同口径对比，堆叠图说明耗时或预算构成，折线图说明时间趋势。
- 图内写清标题、单位、基线和边界；百分比图不隐藏原始值。
- 图表放在引入段落之后、解读段落之前，并紧跟编号图注。不把全部图堆在文档开头，也不集中挪到文末。
- 同一文档中的图使用稳定画布、字号、色彩语义、留白和图注格式。数据记录、图表标签和正文数字必须一致。
- SVG 图表补齐 `<title>`、`<desc>`、`role="img"` 和稳定 `viewBox`；修改后做 XML 解析与整图渲染检查。
- 对应 skill 可用时组合使用：图表设计使用 `data-visualization`，DOCX 使用 `documents`，PPT/PPTX 使用 `Presentations`。当前运行环境没有这些 skill 时，使用现有工具完成等价生成和视觉验证，不假设插件必然存在。

### 按内容性质排版

- 使用无序号且语义稳定的二级/三级标题层级，每节先说本节要回答的问题。
- 段落、表格和图表交替承担“解释、对比、视觉总结”三类职责，不把同一批数据在三处逐字重复。
- 长表格按主题拆分，表前给出阅读目的，表后给出结论和限制。
- 图片不与标题、图注或关键解读分页；转换 DOCX/PDF 后必须重新检查，不假设 Markdown 排版会原样保留。
- 精简只用于消除车轱话、过时中间状态和不影响结论的过程噪音；不用于削掉论证必需的细节。

### 验证并复盘

交付前同时进行内容审查和机械检查。

**内容审查**

- 每个量化结论都能追溯到源数据，公式、单位、样本和舍入正确。
- 问题、定位、方案、结果和推广结论之间一一对应。
- 汇报稿脱离源文档仍能说明关键术语、口径和边界。
- 从代码评审视角查看过度归因、挑选样本、历史状态冒充当前能力和漏写负面结论的风险。

**机械检查**

- 检查标题是否误带序号、重复标题、本地链接、图片数量、图注编号和 Markdown 表格列数。
- 用独立计算重算降幅、预算占比、合计和尾差，不只检查字符串是否存在。
- SVG 使用 `xmllint --noout`或等价 XML 解析器，再做整图与局部视觉检查。
- 运行 `git diff --check`，确认没有空白错误、误删用户文件或把备份文档当作交付件。
- 纯文档修改不需要为了仪式感运行应用构建；说明未运行构建的原因和替代验证。
- DOCX/PDF/PPTX 按对应 artifact skill 渲染成页面或图片后，检查分页、溢出、遮挡、图注和可读性。

## 常见失败模式

| 失败模式 | 修正方式 |
|---|---|
| 使用 `1.`、`1.1` 或 `一、` 给标题编号 | 移除标题序号；顺序关系下沉到正文有序列表 |
| 把行数减少当作排版优化 | 比较精简前后的独立事实、指标定义和限制，丢失即恢复 |
| 汇报稿只有图表和摘要 | 补齐图表前的问题引入、图后的数据解读和证据边界 |
| 全文都是列表 | 因果与取舍改为段落，只保留并列项为列表 |
| 同一数据在正文、表格和图中重复三遍 | 正文解释原因和边界，表格保留精确值，图表强调趋势 |
| 把只有当前值的数据写成提升 | 标注无同口径基线，只与预算或阈值比较 |
| 用通过率证明性能变快 | 作为正确性/无回归证据，另外寻找耗时或频率 A/B |
| 只报最好窗口 | 同时公开完整样本、稳定尾段和非严格 A/B 限制 |
| 图表比正文多出新数据 | 图表只消费证据台账，不自行派生未核对结论 |
| 美化后文档不能独立阅读 | 按背景、定位、指标、结果和边界顺序做脱离源文档复述测试 |

## 交付说明

最终回复说明产物位置、结构调整、新增或保留的量化证据、实际验证、未验证边界和当前提交状态。不用“已美化”这类无法复核的表述代替具体结果。
